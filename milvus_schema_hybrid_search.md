# Milvus Schema & Hybrid Search Deep Dive

## The Core Problem

You have three types of data to index:

| Source | What it looks like | Example query |
|--------|-------------------|---------------|
| **Docs** | Natural language markdown from kubeflow.org | "How do I configure autoscaling in Kubeflow Pipelines?" |
| **Issues** | Bug reports, discussions, error messages from GitHub | "KFP pipeline fails with timeout error on large datasets" |
| **Code** | YAML manifests, Python files from kubeflow/manifests | "What resource limits does the Katib controller request?" or literally `scaleToZeroGracePeriod` |

The question: Can all three live in ONE Milvus collection with ONE embedding model? Or do you need separate collections and a code-specific model (CodeBERT)?

**Answer: One collection, one model, hybrid search.** Here's exactly why and how.

---

## Part 1: The Unified Schema

### Your Current Proposal Schema (What You Have)

From proposal section 1.1:

```
chunk_id        → VARCHAR(128)   — PK, SHA256(file_unique_id + ":" + chunk_index)
file_unique_id  → VARCHAR(512)   — unique per source file or issue
repo_name       → VARCHAR(256)   — e.g. kubeflow/website
file_path       → VARCHAR(512)   — relative path in repo
file_name       → VARCHAR(256)   — basename
citation_url    → VARCHAR(1024)  — link for frontend
chunk_index     → INT64          — position within parent doc
content_text    → VARCHAR(2000)  — the raw text chunk
source_type     → VARCHAR(64)    — "docs" | "issues" | "code" (Partition Key)
vector          → FLOAT_VECTOR(768) — dense embedding from all-mpnet-base-v2
last_updated    → INT64          — unix timestamp
```

### What's Missing: The Sparse Vector

To enable hybrid search, we need to add ONE field and ONE function:

```
sparse_vector   → SPARSE_FLOAT_VECTOR  — BM25 sparse vector (auto-generated by Milvus)
```

Plus a Milvus **built-in function** that auto-generates the sparse vector from content_text:

```python
function = {
    "name": "bm25_embedding",
    "type": "BM25",
    "input_field_names": ["content_text"],
    "output_field_names": ["sparse_vector"],
}
```

**You don't compute sparse vectors yourself.** Milvus does it automatically when you insert data. You only provide `content_text`, and Milvus generates both the BM25 sparse vector internally.

### The AST Parser's Job

The proposal (section 1.3) describes two parsers:

**YAML Parser** — splits on `---` boundaries and top-level resource definitions:

# Parser splits on --- and produces one chunk per resource definition

# Chunk output (what goes into content_text):
# ┌──────────────────── metadata header (prepended by parser) ────────┐

**Python Parser** — splits on function/class boundaries using `ast` module:

# Parser splits on function/class definitions

    self._retry_policy = retry_policy.RetryPolicy(...)

### How These Fit the Unified Schema

For a YAML chunk from `kubeflow/manifests`:

```python
{
    "chunk_id": "sha256(kubeflow/manifests:apps/katib/.../controller.yaml:0)",
    "file_unique_id": "kubeflow/manifests:apps/katib/.../controller.yaml",
    "repo_name": "kubeflow/manifests",
    "file_path": "apps/katib/upstream/components/controller/controller.yaml",
    "file_name": "controller.yaml",
    "citation_url": "https://github.com/kubeflow/manifests/blob/master/apps/katib/.../controller.yaml",
    "chunk_index": 0,
    "content_text": "[Kind: Deployment] [Name: katib-controller] ...<full YAML>...",
    "source_type": "code",   # ← partition key
    "last_updated": 1718899200
}
# "vector" is computed by us: model.encode(content_text)
# "sparse_vector" is auto-computed by Milvus from content_text via BM25
```

**The metadata header** (`[Kind: Deployment] [Name: katib-controller]`) is crucial. By prepending structured metadata to `content_text`, we get two benefits:

1. **Dense vector** captures the semantic meaning: "this is a Deployment for the katib controller"
2. **Sparse vector (BM25)** captures exact keywords: `katib-controller`, `Deployment`, `500m`, `512Mi`

Same schema, same fields, same embedding model — the only difference is `source_type = "code"` instead of `"docs"`.

## Part 3: The Problem with Dense-Only Search for Code

### Why a Single Dense Embedding Model Struggles with Code

Let's say a developer searches for: `scaleToZeroGracePeriod`

**What all-mpnet-base-v2 does with this:**

The model tokenizes it using its WordPiece tokenizer:
```
"scaleToZeroGracePeriod"
→ ["scale", "##To", "##Zero", "##Grace", "##Period"]
```

It then creates a 768-dimensional embedding from these tokens. But the model was trained on natural language (Books, Wikipedia, web forums), not code. The embedding will capture *some* meaning ("something about scaling to zero, a grace period"), but it's fuzzy. The model might rank a docs page about "scaling best practices" HIGHER than the actual YAML file containing `scaleToZeroGracePeriod: "600"`.

**The traditional solution:** Use CodeBERT — a model trained on source code — for code chunks. CodeBERT treats `scaleToZeroGracePeriod` as a meaningful identifier because it was trained on millions of code files.

**The problem with CodeBERT in our setup:**
- You need TWO embedding models (all-mpnet-base-v2 for docs, CodeBERT for code)
- Either TWO separate collections (breaks the unified schema) or complex dual-model indexing
- TWO models to load into memory on the MCP server (doubles RAM)
- The MCP server needs to decide WHICH model to use before knowing if the query is about code
- Maintenance burden doubles

### The Hybrid Search Alternative

Instead of a better model for code, use a **second retrieval mechanism** alongside the dense model:

```
                Query: "scaleToZeroGracePeriod"
                         │
              ┌──────────┴──────────┐
              │                     │
              ▼                     ▼
      Dense Search              Sparse Search (BM25)
   (all-mpnet-base-v2)        (exact keyword matching)
              │                     │
              │ Results:            │ Results:
              │ 1. Scaling docs     │ 1. YAML with scaleToZeroGracePeriod ✓
              │ 2. Autoscaling page │ 2. KServe config docs
              │ 3. KServe overview  │ 3. InferenceService example
              │                     │
              └──────────┬──────────┘
                         │
                    RRF Fusion
                         │
                         ▼
              Final ranking: The YAML file
              with the exact identifier wins
              because it ranked #1 in BM25
```

The BM25 sparse search does **exact token matching** — it will find `scaleToZeroGracePeriod` with perfect accuracy because it's matching the literal string, not trying to understand its semantic meaning.

## Part 4: How BM25 Works (From First Principles)

### What BM25 Actually Computes

BM25 (Best Matching 25) is a scoring function that ranks documents by relevance to a query. For each query term `t` in document `d`:

```
BM25(t, d) = IDF(t) × [TF(t,d) × (k₁ + 1)] / [TF(t,d) + k₁ × (1 - b + b × |d|/avgdl)]
```

Don't memorize the formula. Understand what each piece means:

**TF (Term Frequency):** How many times does the search term appear in this document? More appearances = higher score. But with diminishing returns — appearing 10 times isn't 10× better than appearing once.

**IDF (Inverse Document Frequency):** How rare is this term across ALL documents? 
- "the" appears in every document → IDF ≈ 0 (worthless for ranking)
- "scaleToZeroGracePeriod" appears in 2 documents out of 10,000 → IDF is very high (very useful for ranking)

**Document Length Normalization:** Longer documents naturally contain more terms. BM25 adjusts so that a short, focused YAML file mentioning `scaleToZeroGracePeriod` once scores higher than a long rambling doc that mentions it once among thousands of other terms.

### A Concrete Example

Your collection has 5,000 chunks. A developer searches for `katib controller resources`.

BM25 processes each term:

| Term | IDF (how rare?) | Which chunks score high? |
|------|-----------------|-------------------------|
| `katib` | High (appears in ~50 of 5,000 chunks) | Chunks mentioning Katib |
| `controller` | Medium (appears in ~200 chunks) | Various controller references |
| `resources` | Low (appears in ~500 chunks) | Many K8s manifests mention resources |

A chunk containing ALL THREE terms gets the highest BM25 score.

The chunk with this content would score very high:
```yaml
[Kind: Deployment] [Name: katib-controller]
...
  resources:
    requests:
      cpu: "100m"
```

It contains `katib` (high IDF, rare term), `controller` (medium IDF), and `resources` (low IDF but still contributes). The combination makes it the top BM25 result.

### What a Sparse Vector Looks Like

A sparse vector represents the BM25 scores as a vector where each dimension corresponds to a token in the vocabulary:

```
Vocabulary: {
  "katib": dim_4521,
  "controller": dim_892,
  "resources": dim_1337,
  "deployment": dim_2044,
  "scaleToZeroGracePeriod": dim_9871,
  ... (30,000+ dimensions total)
}

Chunk about katib controller:
sparse_vector = {
  dim_892:   0.72,     # "controller" — medium IDF
  dim_1337:  0.35,     # "resources" — lower IDF
  dim_2044:  0.68,     # "deployment" — medium IDF
  dim_4521:  1.85,     # "katib" — high IDF, rare term = high score
  ... all other dimensions: 0.0
}
```

**Why "sparse"?** Out of 30,000+ dimensions, only ~50 have non-zero values (only the tokens that actually appear in the chunk). 99.8% of the vector is zeros. Compare this to dense vectors where ALL 768 dimensions have non-zero values.

## Part 5: Reciprocal Rank Fusion (RRF)

### The Problem RRF Solves

You have TWO ranked lists from two different search methods. How do you merge them into one final ranking?

You can't just average the scores because dense similarity scores (0.0 to 1.0) and BM25 scores (0 to 30+) are on completely different scales. Scores aren't comparable.

RRF ignores the scores entirely and only looks at **ranks** (positions).

### The RRF Formula

For each document `d` that appears in any result list:

```
RRF_score(d) = Σ   1 / (k + rank(d, R))
               R
```

Where:
- `R` = each result list (dense, sparse)
- `rank(d, R)` = the position of document `d` in result list `R`
- `k` = smoothing constant (default 60 in Milvus)

### Worked Example

A developer asks: `"katib controller resource limits"`

**Dense search results** (semantic):
```
Rank 1: Doc A — "Katib Overview" (kubeflow.org docs page)
Rank 2: Doc B — "How to tune hyperparameters" (docs)
Rank 3: Doc C — katib-controller Deployment YAML (code)
Rank 4: Doc D — GitHub Issue "Katib OOM on large experiments"
```

**Sparse (BM25) search results** (keyword):
```
Rank 1: Doc C — katib-controller Deployment YAML ← exact match on all terms
Rank 2: Doc D — GitHub Issue (mentions "resource limits")
Rank 3: Doc A — "Katib Overview" (mentions some terms)
Rank 4: Doc E — Katib config reference (mentions "controller")
```

**RRF calculation** (k=60):

| Document | Dense Rank | Sparse Rank | RRF Score |
|----------|-----------|-------------|-----------|
| **Doc C** (YAML) | 3 → 1/(60+3) = 0.01587 | 1 → 1/(60+1) = 0.01639 | **0.03226** ← WINNER |
| **Doc A** (overview) | 1 → 1/(60+1) = 0.01639 | 3 → 1/(60+3) = 0.01587 | **0.03226** ← TIE |
| **Doc D** (issue) | 4 → 1/(60+4) = 0.01563 | 2 → 1/(60+2) = 0.01613 | **0.03175** |
| **Doc B** (tuning) | 2 → 1/(60+2) = 0.01613 | not found → 0 | **0.01613** |
| **Doc E** (config) | not found → 0 | 4 → 1/(60+4) = 0.01563 | **0.01563** |

**Final ranking:** Doc C (the actual YAML) ties with Doc A (the overview docs page) at the top. Both are highly relevant. Doc B (only found by dense search) and Doc E (only found by BM25) rank lower because they only appeared in one list.

### Why k=60?

The constant `k` controls how much rank position matters:
- **Small k (e.g., 1):** Top-ranked documents get dramatically more weight. Position 1 vs 2 is a big difference.
- **Large k (e.g., 60):** Positions are smoothed out. The algorithm cares more about "did you appear in multiple lists?" than "were you #1 vs #2?"

k=60 is the standard because it balances both concerns — appearing in multiple lists is rewarded, but being ranked higher still matters.

## Part 6: Why This Eliminates the Need for CodeBERT

Here's the complete argument:

### The Claim

> "Code needs a code-specific model like CodeBERT to handle identifiers properly."

### The Counter-Argument (Why Hybrid Search Solves This)

The reason people want CodeBERT is to handle queries like:
- `scaleToZeroGracePeriod` (exact identifier lookup)
- `InferenceService` (CamelCase K8s resource type)
- `--enable-auto-tool-choice` (CLI flags)
- `gpu-memory-utilization` (config parameters)

These are all **exact keyword matching problems**, not semantic understanding problems. You don't need a model to "understand" what `scaleToZeroGracePeriod` means — you need to find the document that contains that exact string.

**BM25 does this perfectly.** It's a keyword matcher. It finds exact strings.

Meanwhile, the dense model (all-mpnet-base-v2) handles the OTHER type of code query:
- "How do I configure GPU memory for model serving?" → semantic match to YAML containing `gpu-memory-utilization`
- "What scaling behavior does KServe use?" → semantic match to InferenceService config

```
┌─────────────────────────── Query Types ───────────────────────────────┐
│                                                                       │
│  Exact Identifier Lookup          Semantic Concept Search             │
│  "scaleToZeroGracePeriod"        "how to configure GPU memory"       │
│  "--enable-auto-tool-choice"     "what does the Katib controller do"  │
│  "InferenceService"              "scaling behavior for model serving" │
│         │                                  │                          │
│         ▼                                  ▼                          │
│    BM25 Handles This              Dense Model Handles This            │
│    (exact token match)            (semantic similarity)               │
│         │                                  │                          │
│         └──────────── RRF Fusion ──────────┘                          │
│                           │                                           │
│                    Best of both worlds                                │
│                    No CodeBERT needed                                 │
└───────────────────────────────────────────────────────────────────────┘
```

### What CodeBERT Would Add (and Why It's Not Worth It)

CodeBERT WOULD give slightly better semantic understanding of code structure — it knows that `def __init__(self)` is a constructor, that `import torch` relates to PyTorch. But:

1. **Our code chunks are 80% YAML, not complex Python.** YAML is closer to structured text than to source code. all-mpnet-base-v2 handles it well.
2. **The prepended metadata header helps the dense model.** By adding `[Kind: Deployment] [Name: katib-controller]`, we give the general model explicit natural-language context about what the code is.
3. **Maintaining two models doubles infrastructure cost.** Two SentenceTransformer models in memory, two embedding calls per ingestion, two-model query routing logic.
4. **BM25 covers the exact-match weakness.** The main reason people want CodeBERT is identifier matching — BM25 does this better than any neural model because it's a deterministic string match.

## Part 7: The Complete Updated Schema (With Hybrid Search)

```python
from pymilvus import MilvusClient, DataType, Function, FunctionType

def create_collection(client: MilvusClient):
    schema = MilvusClient.create_schema()

    # ── Primary Key ──
    schema.add_field(
        field_name="chunk_id",
        datatype=DataType.VARCHAR,
        max_length=128,
        is_primary=True,
        description="SHA256(file_unique_id + ':' + chunk_index)"
    )

    # ── Source Identification ──
    schema.add_field(field_name="file_unique_id", datatype=DataType.VARCHAR, max_length=512)
    schema.add_field(field_name="repo_name", datatype=DataType.VARCHAR, max_length=256)
    schema.add_field(field_name="file_path", datatype=DataType.VARCHAR, max_length=512)
    schema.add_field(field_name="file_name", datatype=DataType.VARCHAR, max_length=256)
    schema.add_field(field_name="citation_url", datatype=DataType.VARCHAR, max_length=1024)
    schema.add_field(field_name="chunk_index", datatype=DataType.INT64)

    # ── Content ──
    schema.add_field(
        field_name="content_text",
        datatype=DataType.VARCHAR,
        max_length=8000,           # increased from 2000 for code chunks
        enable_analyzer=True,      # ← required for BM25
        enable_match=True,         # ← required for BM25
        analyzer_params={
            "tokenizer": "standard",
            "filter": ["lowercase"]
        },
        description="Raw text chunk (docs, issues, or code with metadata header)"
    )

    # ── Partition Key ──
    schema.add_field(
        field_name="source_type",
        datatype=DataType.VARCHAR,
        max_length=64,
        is_partition_key=True,     # ← Milvus manages physical partitions automatically
        description="docs | issues | code"
    )

    # ── Dense Vector (semantic search) ──
    schema.add_field(
        field_name="dense_vector",
        datatype=DataType.FLOAT_VECTOR,
        dim=768,
        description="all-mpnet-base-v2 embedding"
    )

    # ── Sparse Vector (BM25 keyword search) ──
    schema.add_field(
        field_name="sparse_vector",
        datatype=DataType.SPARSE_FLOAT_VECTOR,
        description="Auto-generated by Milvus BM25 function"
    )

    # ── Timestamp ──
    schema.add_field(field_name="last_updated", datatype=DataType.INT64)

    # ── BM25 Function (auto-generates sparse_vector from content_text) ──
    schema.add_function(Function(
        name="bm25_embedding",
        function_type=FunctionType.BM25,
        input_field_names=["content_text"],
        output_field_names=["sparse_vector"],
    ))

    # ── Indexes ──
    index_params = MilvusClient.prepare_index_params()

    # Dense index (for semantic ANN search)
    index_params.add_index(
        field_name="dense_vector",
        index_type="AUTOINDEX",
        metric_type="COSINE",
    )

    # Sparse index (for BM25 keyword search)
    index_params.add_index(
        field_name="sparse_vector",
        index_type="SPARSE_INVERTED_INDEX",
        metric_type="BM25",
    )

    # Create collection
    client.create_collection(
        collection_name="docs_rag",
        schema=schema,
        index_params=index_params,
    )
```

### Key Changes from the Proposal Schema

| Change | Why |
|--------|-----|
| `vector` → `dense_vector` | Clarity: distinguish from the new sparse vector |
| NEW: `sparse_vector` (SPARSE_FLOAT_VECTOR) | BM25 keyword matching for code identifiers |
| NEW: BM25 function linking `content_text` → `sparse_vector` | Auto-generates sparse vectors on insert |
| `content_text` max_length: 2000 → 8000 | Code chunks (YAML manifests) can be larger than docs chunks |
| `enable_analyzer=True` on `content_text` | Required for Milvus to tokenize text for BM25 |
| NEW: SPARSE_INVERTED_INDEX on sparse_vector | Required index type for BM25 search |

## Part 8: How the MCP Server Uses Hybrid Search

The updated `search_kubeflow_docs` tool:

```python
from pymilvus import AnnSearchRequest, RRFRanker

@mcp.tool()
def search_kubeflow_docs(query: str, top_k: int = 5, source_filter: str = "all") -> str:
    """Search Kubeflow documentation, issues, or code using hybrid search."""
    _init()

    # ── Step 1: Compute dense embedding for semantic search ──
    dense_vector = model.encode(query).tolist()

    # ── Step 2: Build the two search requests ──

    # Dense search (semantic understanding)
    dense_req = AnnSearchRequest(
        data=[dense_vector],
        anns_field="dense_vector",
        param={"metric_type": "COSINE", "params": {"nprobe": 32}},
        limit=top_k * 2,          # retrieve more candidates for RRF
    )

    # Sparse search (BM25 keyword matching)
    # Note: for BM25, you pass raw text — Milvus tokenizes it automatically
    sparse_req = AnnSearchRequest(
        data=[query],             # ← raw text, not a vector!
        anns_field="sparse_vector",
        param={"metric_type": "BM25"},
        limit=top_k * 2,
    )

    # ── Step 3: Build search kwargs with partition filter ──
    search_kwargs = {
        "collection_name": "docs_rag",
        "reqs": [dense_req, sparse_req],
        "ranker": RRFRanker(k=60),
        "limit": top_k,
        "output_fields": ["content_text", "citation_url", "file_path", "source_type"],
    }

    # Apply partition filter if not "all"
    if source_filter != "all":
        search_kwargs["partition_names"] = [source_filter]

    # ── Step 4: Execute hybrid search ──
    hits = client.hybrid_search(**search_kwargs)

    # ── Step 5: Format results ──
    if not hits or not hits[0]:
        return "No results found for your query."

    results = []
    for i, hit in enumerate(hits[0], 1):
        entity = hit.get("entity", {})
        entry = f"### Result {i}"
        entry += f"\n**Source:** {entity.get('citation_url', '')}"
        entry += f"\n**Type:** {entity.get('source_type', '')}"
        entry += f"\n**File:** {entity.get('file_path', '')}"
        entry += f"\n\n{entity.get('content_text', '')}\n"
        results.append(entry)

    return "\n---\n".join(results)
```

### What Happens at Search Time

```
Query: "scaleToZeroGracePeriod KServe configuration"

Step 1: Dense embedding
  model.encode("scaleToZeroGracePeriod KServe configuration")
  → [0.12, -0.34, 0.56, ...] (768 dimensions)
  This captures semantic meaning: "something about KServe scaling config"

Step 2: BM25 tokenization (done by Milvus internally)
  "scaleToZeroGracePeriod KServe configuration"
  → tokens: ["scaletozerogracperiod", "kserve", "configuration"]
  Milvus searches its inverted index for these exact tokens

Step 3: Two searches run in parallel inside Milvus

  Dense search finds:
    Rank 1: KServe autoscaling docs page (high semantic similarity)
    Rank 2: InferenceService configuration guide
    Rank 3: YAML with scaleToZeroGracePeriod (some semantic match)

  BM25 search finds:
    Rank 1: YAML with scaleToZeroGracePeriod (exact token match!)
    Rank 2: KServe docs mentioning "configuration"
    Rank 3: GitHub Issue about scaling

Step 4: RRF fuses the rankings
  → YAML with scaleToZeroGracePeriod ranks #1 (appeared high in both lists)
  → KServe docs page ranks #2
  → Configuration guide ranks #3
```

### The Critical Advantage

**Without hybrid search** (dense only):
- Query `scaleToZeroGracePeriod` → dense model might rank a generic "KServe overview" docs page higher than the actual YAML containing the exact identifier.

**With hybrid search** (dense + BM25):
- BM25 guarantees the YAML file containing `scaleToZeroGracePeriod` is ranked #1 in the sparse results.
- RRF then ensures it appears at or near the top of the final results.
- You get both semantic understanding AND exact keyword precision.

## Part 9: How Ingestion Works for Each Source Type

### Data Flow During Ingestion

```
KFP Pipeline
    │
    ├── Docs Ingestion
    │   ├── Scrape kubeflow.org markdown
    │   ├── Chunk by headings/paragraphs
    │   ├── For each chunk:
    │   │   ├── Compute dense_vector = model.encode(content_text)
    │   │   ├── Set source_type = "docs"
    │   │   └── Upsert to Milvus (sparse_vector auto-generated from content_text)
    │
    ├── Issues Ingestion
    │   ├── Fetch from GitHub Issues API
    │   ├── Chunk by issue body paragraphs
    │   ├── file_unique_id = "kubeflow/kubeflow:issue/1234"
    │   ├── For each chunk:
    │   │   ├── Compute dense_vector = model.encode(content_text)
    │   │   ├── Set source_type = "issues"
    │   │   └── Upsert to Milvus
    │
    └── Code Ingestion
        ├── Clone kubeflow/manifests
        ├── AST parse:
        │   ├── YAML: split on --- boundaries, prepend [Kind] [Name] metadata
        │   └── Python: split on function/class boundaries, prepend signature
        ├── file_unique_id = "kubeflow/manifests:apps/katib/.../controller.yaml"
        ├── For each chunk:
        │   ├── Compute dense_vector = model.encode(content_text)
        │   ├── Set source_type = "code"
        │   └── Upsert to Milvus (sparse_vector auto-generated)
```

**All three source types go through the same embedding model and into the same collection.** The only differences:
1. `source_type` value ("docs" vs "issues" vs "code") — used for partition routing
2. How the original content is chunked (paragraphs vs AST boundaries)
3. Whether metadata headers are prepended (code chunks get `[Kind: X]` headers)

|---|---|
| *"Why not use CodeBERT for code?"* | Our code is 80% Kubernetes YAML, not complex source code. The main weakness of general models with code is exact identifier matching — BM25 sparse search solves this perfectly without a second model. Hybrid search gives us both semantic understanding AND keyword precision. |
| *"How does one model handle both English docs and YAML?"* | The AST parser prepends natural-language metadata headers to code chunks: `[Kind: Deployment] [Name: katib-controller]`. This gives the dense model explicit semantic context. The BM25 sparse vector handles the exact YAML tokens. |
| *"What if someone searches for an exact config value like `0.90`?"* | BM25 handles this. The token `0.90` in the YAML chunk `--gpu-memory-utilization=0.90` will be found by exact match. Dense search alone would struggle with numeric values. |
| *"Why one collection instead of separate collections per source type?"* | (1) Partition keys give physical isolation without schema duplication. (2) Cross-partition search is handled by Milvus at the C++ level — no application-level fan-out. (3) One schema to maintain, one index to manage, one embedding pipeline. (4) The agent can search "all" or scope to "docs"/"code"/"issues" in a single query. |
| *"What's the performance impact of hybrid search?"* | Two ANN searches instead of one, plus the RRF reranking. In practice, the latency increase is <10ms because both searches run in parallel inside Milvus, and RRF is a simple arithmetic operation over the result sets. |
| *"Why increase content_text from 2000 to 8000 chars?"* | YAML Kubernetes manifests can be verbose. A full Deployment spec with containers, volumes, env vars, resource limits can easily exceed 2000 chars. Truncating it would lose critical configuration details. 8000 chars accommodates the largest K8s resource definitions. |
